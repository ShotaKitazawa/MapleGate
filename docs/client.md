# Client

The purpose: friends play the game with the game's traffic going through the us-west-2 node, without knowing AWS. The server side is done and checked (`docs/e2e.md`); this is the plan for the client.

## Phases

| Phase | What | Needs a person on a real machine |
|---|---|---|
| 4 | The client core, driven from a terminal: sign in, ask, wait for approval, bring the tunnel up, take it down and leave no routes behind | yes, macOS first; Windows follows with the same shape |
| 5 | The privileged daemon and its IPC, the tray UI, the installers, a one page guide for friends | yes |
| 6 | Operations: Budgets, error notices, a janitor liveness alarm | no |

Why the cut is between 4 and 5: the risky parts are the tunnel, the routes, recovery after a Wi-Fi change and IPv6 leaks, and all of them can be checked from a terminal. The UI and the installers are a thin layer over behaviour that is already settled, so they come after.

### Where the privilege boundary sits

The daemon and its IPC exist only so that an unprivileged tray UI can ask for something privileged. Phase 4 has no UI, so building them there would not check anything that Phase 4 is for. What Phase 4 does instead:

- Everything that does not need root runs as the user: sign in (`auth`), the API calls (`api`), the session state machine (`session`). Opening a browser and keeping tokens in the user's home are awkward as root, and this is the shape the tray UI will have.
- Everything that needs root is one entry, `gamevpn tunnel`, started with `sudo`. It reads one JSON object on stdin with the same fields as the IPC `Up{config, private_key}` of Phase 5, brings up the interface and the routes, and takes them down on SIGINT, SIGTERM, or when stdin closes. In Phase 5 the daemon receives that same object over a socket instead of stdin, and nothing else changes.
- The private key is generated by the unprivileged process and handed over on stdin. It is never written to disk and never printed.

## Decisions

- **Sign in**: the client does the Identity Center device flow itself (RegisterClient, StartDeviceAuthorization, CreateToken, GetRoleCredentials) so friends need no AWS CLI. The browser opens only when there is no valid token. Role credentials are fetched again before they expire, so a long session never asks again.
- **Settings**: start URL, region, account, role name and API URL are in a small file, `~/Library/Application Support/gamevpn/config.json` on macOS, with the values of this deployment as defaults. None of them is secret.
- **Tunnel**: wireguard-go in the process (utun), configured over UAPI. Not a dependency on a separate WireGuard install.
- **Routes**: `0.0.0.0/1`, `128.0.0.0/1`, `::/1` and `8000::/1` into the tunnel (so the default route is untouched and IPv6 cannot leak around it), and the node's endpoint address kept on the original gateway. They are removed on every way out, including a crash of the parent.
- **Session**: the unprivileged process polls the session while the tunnel is up and ends the tunnel only on a terminal status. A failed poll never ends it.

## Done when (Phase 4, macOS)

1. `gamevpn up` from a fresh machine state: browser sign in once, a Discord approval, then the tunnel; the visible address is the node's.
2. A second `up` after the token is cached opens no browser.
3. Switching Wi-Fi recovers the tunnel, or ends it with a clear message.
4. After a normal end, Ctrl-C, `kill` of either process, or closing the terminal, no route and no interface of ours remains.
5. `curl -6` fails or goes through the tunnel.
6. The game logs in through the tunnel (F1 in `docs/e2e.md`).

Tests: everything except the part that touches the OS is a unit test (the device flow against a fake server, the session machine, the route plan as a pure function). The OS part is a manual list, `docs/e2e.md`.

## Phase 5 design

The privileged half becomes a daemon, `gamevpnd` (a LaunchDaemon on macOS), and `gamevpn` becomes a tray app that asks it for the tunnel. `tunnel.Run` is unchanged: the daemon runs it where `gamevpn tunnel` did, and the object it receives is the same `tunnel.Up` that was on stdin.

- **IPC**: a Unix socket at `/var/run/gamevpnd.sock`. One JSON line in, one JSON line out per call: `up`, `down`, `status`. The daemon accepts only root and the user who owns the console, checked with the peer credentials of the connection, not with file permissions alone.
- **The tunnel outlives the UI.** A tray app that crashes in the middle of a game must not cut the player. `status` returns the session id the tunnel was started for, so a restarted UI picks the tunnel up again and keeps watching that session.
- **A tunnel nobody looks after is taken down.** The UI calls `status` every few seconds, and that is also the heartbeat. After 15 minutes without a call the daemon takes the tunnel down. Without this rule a dead UI would leave the tunnel up, its handshakes would keep the session extended, and the node would never stop. The window is long enough for a restart and short enough to bound the cost.
- **The UI closes the session** at the server (it holds the credentials; the daemon never does). Taking the tunnel down because nobody looks does not close the session; the node closes it as `idle` within about 10 minutes.
- **Tray**: one Go code base for both systems (`fyne.io/systray`), because maintaining a native UI per system is more than this project can carry. States: signed out, waiting for approval, connected (with how long it has been up, not the time left: the session is extended while it is in use, so the expiry is always about the same), error.
- **Installers**: a macOS pkg that installs the two binaries, loads the LaunchDaemon and starts the tray at login; the Windows installer follows the macOS one. Neither is signed or notarized, so the guide for friends says how to get past Gatekeeper and SmartScreen.
